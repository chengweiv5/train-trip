# v2.0 原生账号密码登录与真实乘车人验证

日期：2026-09-30，Asia/Shanghai。

## 结论

**单手机原生账号密码 + 短信验证已在真机成功建立本应用会话，并读取到 7 位乘车人。**

- 用户在手机内输入账号、密码、绑定证件后四位和短信验证码；助手未读取输入框、原始乘车人资料、Cookie 或 Token。
- 登录流程没有打开网页登录页面，没有使用二维码，也没有提取已安装 12306 App 的私有登录数据。
- 原生页面展示脱敏乘车人信息；“读取到 7 位”不代表 7 位均满足所有票种或下单资格，资格判断仍需独立核验。
- **生产查单、候补组合初始化和真实候补提交仍未接通。** 本轮未发送候补订单，没有取消或支付。

## 已否定路线

此前扫码实验仅证明匿名挑战可创建。用户明确指出单手机不适合扫描自身屏幕，随后选择本应用账号输入。

已停止扫码进程并删除手机、电脑上的临时二维码。生产工厂不再绑定扫码服务，HTTP 路径白名单不包含二维码创建/轮询，界面没有扫码入口。源码中的扫码服务与离线实验测试暂保留为未启用实验，不作为已交付产品功能。

## 实现与安全边界

1. 原生 Compose 账号、密码表单；服务端要求短信时显示证件后四位和六位验证码字段。
2. 登录前调用 `checkLoginVerify`，按官方返回决定是否需要短信。只有用户主动点击才请求短信；一分钟冷却，验证信息绑定账号且短时有效。
3. 密码编码使用 Bouncy Castle 1.79 的 SM4 实现，按官方脚本的 ECB/PKCS7/Base64 格式发送；只用于协议兼容，**不能替代 HTTPS，也不把公开固定编码密钥描述成额外保密能力**。
4. 登录成功后执行 `auth/uamtk → otn/uamauthclient`，随后验证会话、稳定账号标识、乘车人响应，并再次核对账号未切换。只有完成这些检查才记录 `AUTHENTICATED`。
5. 无凭据中转服务器；请求仅发送到固定的 `https://kyfw.12306.cn`。不跳转、不忽略 TLS 错误、不自动重试登录或短信。
6. 会话 Cookie 保存在应用内存中，不持久化。密码/验证码不放入 ViewModel 状态或保存状态；请求使用的字符数组及时清零；页面离开/进入后台清空敏感输入。JVM/Compose 的临时字符串无法保证物理内存即时擦除，因此不作这一承诺。
7. 登录和乘车人页面启用 `FLAG_SECURE`。开发诊断仅包含状态类别及乘车人数，不包含账号、密码、证件、验证码、Cookie 或乘客对象。
8. 服务端若要求当前未接通的滑块或登录后额外验证，明确停止，不伪造验证字段、不绕过。此次实测成功的是**短信分支**，不代表所有认证分支均可用。
9. 订单 Gateway 仍是关闭状态；Transport 目前仅开放认证与乘车人读取相关路径，不开放 `confirmHB` 等订单提交路径。
