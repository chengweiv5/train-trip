# v2.0 自动候补实现计划

**Goal:** 按已确认的 17 屏设计实现独立候补入口，以及一次授权后自动排除明确拒绝项、继续全部剩余需求的安全提交流程。

**Architecture:** 纯 Kotlin 状态机持有请求身份、需求与乘客绑定和恢复规则；持久化协调器先落盘再调用平台适配器。Android 的查询/认证/页面层复用现有控件，不将网页会话和 App RPC 混用。平台适配器未经实际认证与返回结构核验前，不连接用户账号提交真实订单。

**Tech Stack:** 现有 Kotlin/JVM core、coroutines、JUnit4；Android/Compose 四主题。

**Spec:** `docs/superpowers/specs/2026-09-29-v2.0-waitlist-order-design.md`

## 执行与范围

用户在确认配色后明确要求“设计完成后直接进入代码开发”，本任务采用当前会话原生执行，不再等待锁屏保存或新增计划确认。先完成可独立测试的业务状态机与协调器；页面与已验证平台适配按后续任务推进。公开测试边界为状态机事件/效果接口、协调器的 Gateway / Store 边界，不测试私有方法。

开发阶段不推送、不发布、不使用真实账号下单、不自动取消订单；开发仍在 `codex/v2.0-development`。既有无关工作区改动全部保留。2026-09-30 查询/选择接入验收后，用户单独授权“提交并推送”，仅开放功能分支提交和快进推送到 `origin/main`，不包含发布或真实下单。

## Global Constraints

- 每轮一次提交全部剩余需求，不暗中分组；只自动排除可准确归因的受限需求。
- 一次明确拒绝后的自动续提不再询问用户；创建订单立即结束自动提交。
- 超时、网络中断、未知返回、停止及退后台后不得盲目重发；先核对未决订单。
- 同一账号、实际乘客身份集合和票种与请求绑定；人数相同不代表相同乘客。
- 实际组合上限由经验证平台能力提供，不能写死未核实上限。
- 认证与乘客不透明标识不得写入日志；本阶段状态持久化仅处理非凭证引用。
- 四主题均保留；大卡与长段文字使用主题角色，状态颜色仅小图标/短标签。

## Review Focus

1. 超时后迟到成功：显示真实订单，不再次提交。
2. 停止期间已发请求成功：仍显示订单，不伪装撤销。
3. 账号/乘客替换及陈旧事件：不得写入当前任务或继续错误身份请求。
4. 返回归因不完整或指向集合外项目：暂停，不猜测删除。
5. 落盘失败和进程重建：未持久化不发送；已发/可能已发的请求先查单。
