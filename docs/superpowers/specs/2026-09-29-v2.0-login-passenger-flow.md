# v2.0 登录与真实乘车人流程

**已被用户最新澄清取代**：当前目标正式定为候补下单，按[候补下单设计](2026-09-29-v2.0-waitlist-order-design.md)执行。以下“真实提交待确认”属于历史决策记录，不再要求用户重复确认。

当前交互提案。用户已确定接入方向：登录 12306、读取当前账号乘车人、勾选实际乘客，再判断蓝色候补车次的请求是否被接受。尚未授权真实订单提交或批量试单。

原先只填写人数的设计由本稿的实际乘车人选择取代。原 8 页“只填人数、纯探测通过”预览保留为历史提案，不能作为实现依据。

## 已确定的前半段

1. 登录入口：展示 12306 账号状态。具体认证方式必须通过接入验证后确定；不能假定从系统浏览器登录即可提取官方 App 的会话，或网页登录会话一定兼容 App RPC。
2. 读取乘车人：认证成功后，通过同一已验证会话对应的乘车人接口取得记录与标识。网页登录和 App 接口分别有自己的返回结构，不能混用 `allEncStr` 与 `enc_no`。
3. 勾选乘车人：按官方返回状态展示可选或待核验。显示姓名及证件尾号，人数由已选记录自动计算，不再提供可与名单不一致的独立数字输入。儿童、学生等票种按实际记录和出行日期核对。
4. 查询蓝色候补候选：车次、席别、区间、日期、兑现期限与已选乘客组成完整请求条件。候选状态只能描述当前入口是否受限，不标成“5 人已通过”。

用户不输入、编辑或看到加密串。`enc_no` / `allEncStr` 是程序从对应官方流程获取的不透明值；其绑定和有效期尚待验证。使用后端返回值不代表自动具备客户端认证、业务和风险校验资格。

## 提交语义待用户确认

根据已检查的网页和官方 Android 内置候补流程，能够给出最终接受/拒绝结果的操作属于正式提交。实现前必须明确是否接受其成功时生成真实待支付订单。

本次提供可评审的方案：

- 选定一个日期、准确区间、车次、席别以及 5 位乘车人，展示“确认候补请求”页。
- 页面明确“成功时会生成待支付订单”，按钮使用“尝试提交候补订单”，不使用“仅探测”。
- 用户确认后只发送该请求；成功即显示订单结果。不自动尝试下一车次、不付款、不自动取消。
- 明确拒绝：展示该次返回的业务原因，保留乘客名单，由用户选择其他车次。
- 已创建：展示订单号、预付款、支付截止时间，以上均取真实返回。不能把待支付订单显示成“校验通过”。
- 超时/连接中断/未知响应：先查该次订单状态，不立刻重发。查询未找到订单也可能存在时序延迟，只有确定未创建且后续动作具备授权才能重试。
- 用户点击停止，只停止后续操作，不能把已发出请求当作撤销成功；已产生的订单仍需展示和处理。

这是一种真实提交的替代方案，不等同于原目标要求的批量无副作用容量探测。若用户不接受生成订单，则继续以只读前置筛选为边界，不能通过构造乘客、提交后自动取消等手段伪装成纯查询。

## 会话与数据边界

同一登录身份、已选乘客身份集合、票种与行程条件必须绑定。5 人换成另一组 5 人同样使旧判断失效。账号切换/退出清除乘客缓存与已选标识，不沿用旧账号的订单或结果。会话过期后重新认证并刷新乘客列表，不盲目重放旧标识。

身份资料、会话令牌和乘客标识不进入日志、异常上报或版本库。仅持久化必要的会话材料，使用 Android 的受保护存储；默认不另存原始密码。设计示例中的姓名、证件尾号、账号尾号均为虚构。
