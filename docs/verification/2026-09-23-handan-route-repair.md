# 邯郸玩法为空：修复与真机验证

## 问题与改动

手机原有邯郸缓存显示“暂未整理出可靠路线”。搜索已经获得民间攻略，但 DeepSeek 的第一轮输出可能引用不完整、顺序与原文不符，或把不同文章拼为两天。原代码会过滤整条路线并保存空玩法。

现在第一次整理后若没有可用路线、且搜索资料中有行程原文，会对已通过校验的景点最多追加一次路线专项整理。仍调用用户配置的 DeepSeek 模型，搜索继续使用豆包。专项输入只包含已收录景点 ID、名称及相关原文，不改变已生成景点和美食。

专项结果仍通过原有校验：连续原文、包含所选景点、原文顺序、两天同一来源。请求失败、输出格式错误或仍无合格路线时保留已有图文，不反复请求。不增加景点/美食数量上限，不清除其他城市，不自动批量生成。

README 已更正：原十张图片为模拟器界面；邯郸图文来自电脑端成功样本导入，不能作为真机完整生成成功的证据。

## 验证结果

- 最小失败样本：原实现得到 2 个景点、0 条路线；同一回归用例在原实现失败，修复后通过。
- 真实 DeepSeek 补救：重放第一次失败输出后进行一次真实请求，得到 1 条路线，连续原文验证通过。
- 电脑端全新豆包搜索＋DeepSeek：16 篇资料，4 个景点、3 种美食。首轮解码为 0 条路线，专项整理后得到 1 日和 2 日各一条，原文验证通过。
- 核心测试 135 项通过；随后加入手机实际响应回归，路线修复测试共 4 项通过。Android Debug、Release、AndroidTest 构建通过；本轮未额外运行模拟器界面测试。

## Mate 60 Pro 实际验证

用户允许操作手机后，先记录旧缓存的空玩法页面，备份已安装 APK。同证书、不可调试的修复包覆盖安装，首次安装时间不变，服务配置、收藏和已有图片保留。

首次更新仍为空，因此没有把电脑结果当作真机成功。第二次使用同业务代码的临时诊断构建，记录不含密钥/请求头的搜索原文、模型输出及缓存合并结果：

1. 初始一日路线原文顺序为街区→公园→博物馆，模型却填写博物馆→公园→街区，被拒绝。
2. 初始两日路线还存在非连续引文与跨文章问题，被拒绝。
3. 专项整理得到一日路线“邯郸博物馆 → 丛台公园 → 邯郸道历史文化街区”，通过核验，合并后保存成功。
4. 专项两日路线第二天错误引用了当天原文没有的三个景点，被拒绝。真机当前只验收到一日玩法。

最终移除临时诊断代码与手机临时诊断文件，再覆盖安装最终包。冷启动后原生玩法页仍显示上述一日路线；原有回车巷 3 张图片可读；离线内容仍只有邯郸，累计 10 景点、4 美食。手机安装包回拉后与最终包逐字节相同。

- 包名：`cn.traintrip.app`；版本仍为 `0.9.0` / code 14，本轮没有发布新版本或覆盖公开 v0.9.0 附件。
- 设备证书 SHA256：`cae9ed8a5c544fc2088161792d4811d60ba988265d76b476d3857ab716b6c603`，与升级前一致。
- 最终手机 APK SHA256：`0eed75e30f022ae79d91c209c202bc4181ce9eaa57d8e07c7ea5ea5680a41b8d`。
- 真机安装包不含诊断导出逻辑，APK 与待提交文件均完成实际凭证匹配检查，无命中。

这次修复提高了有原文时的恢复能力，不能保证每次搜索都产生路线；两日玩法仍取决于当前已收录景点与原文覆盖。
