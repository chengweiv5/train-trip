# 全量刷新保留缓存景点与美食

用户已确认：保留全部旧条目，合并新增，允许超过原来的 5 个景点；每条目 3 张、每城市 100 张图片保持不变。本次是数据合并修复，不变更界面布局。

## 复现与根因

`GuideRefreshRetentionTest.fullRefreshKeepsCachedGuangfuWhenNewSearchOmitsIt` 在实际 ViewModel → repository → Android store 路径稳定失败：旧缓存为广府古城和博物馆，新检索仅返回博物馆，保存结果只剩博物馆。当前 `saveTextKeepingPhotos` 只将旧图映射到新正文，没有合并景点或美食；随后的清理还可能删除被遗漏条目的图。检索遗漏或原文校验失败不能作为删除旧条目的依据。

## 合并规则

推荐并采用按条目合并；拒绝继续整份覆盖，也不采用“最多 5 个、旧条目优先”的截断方案，后者与用户选择冲突。

- 在核心 `GuideRefreshPolicy.merge(previous, fresh)` 统一合并；repository 在 `prepare` 前执行，所以 Android 的首次正文提交已经包含旧条目。
- 旧景点和美食维持顺序及身份，新条目追加。只有相同城市、同类型、名称精确匹配或唯一括号别名匹配才更新同一条目；不能按生成的顺序 ID 或包含关系合并。歧义时保留为独立条目。
- 匹配景点使用新正文等字段并保留旧名称和 ID，旧来源/证据在新值缺失时保留；未命中的旧条目完整保留。新增景点分配不冲突的 ID；新玩法中的 ID 映射到合并结果，避免把新 p1 错绑到旧 p1。
- 美食名称去重，规则同景点。来源按 URL 合并，重复 URL 采用新的核对日期。全局简介等采用新版本。新玩法若为空则保留旧玩法；有新玩法时按天数更新，旧有其他天数玩法保留。
- 模型单次仍最多生成 5 景点/6 美食/10 来源，缓存是历次有效结果合并集合，不再套用这些单次上限。分离 `validateGenerated` 与 `validateCached`，两者仍检查正文、ID、玩法引用、来源与图片有效性。
- 旧照片由 Android store 检查可用性后优先保留；核心合并不复用顺序 ID 绑定图片。缺图条目仍按 3/100 和备用来源规则补图。
- 缓存读取不得继续使用旧 512 KiB 小限额导致合并后保存成功却打不开；保留 16 MiB 存储保护，读写采用同一限额，超限在原子替换前失败并保留原缓存。
- 错城市输入在写入前拒绝。检索或生成整体失败、取消时保留旧内容；成功合并后也不能删除未命中的旧条目图片。

## 验证和范围

核心回归覆盖遗漏旧条目、超过 5/6/10、重名/别名、p1 重用、玩法映射、重复刷新幂等、跨城市拒绝、累计缓存与单次输出分别校验。Android 原始复现必须转绿，补充超过 5 景点持久化重读、旧图片保留、可用旧图不触发重复下载。运行 core 全测、Debug/Release/testAPK 构建、lint 和相关 Android 回归。源码备份 `.verification-private/handan-refresh/before.tar`。

修复能保证今后的刷新不再因本次未检索到而删除条目；手机上已经被旧版本覆盖的原始文字/图片，未取得旧数据前不能宣称已恢复。此轮不消耗真实模型/搜索额度，不推送或发布。
