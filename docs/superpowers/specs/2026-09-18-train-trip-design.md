# Train Trip 首版设计

状态：用户已确认产品范围；2026-09-18 补充目标设备。当前阶段为真实票源可行性验证，完整 App 尚未实现。

## 目标与设备

给用户本人使用：节假日先找出有票可去的城市，再选择旅行目的地，最终在 12306 完成购票。

- 目标真机：华为 Mate 60 Pro，HarmonyOS 4.2.0。
- 交付形式：Android APK，Kotlin + Jetpack Compose，不依赖 Google Play Services。
- 开发基线：minSdk 26，compileSdk/targetSdk 36。设备实际 Android API 等级必须通过真机 `getprop` 核实；HarmonyOS 版本号不能直接换算为 Android API 等级。
- 使用本地筛选偏好和前台查询；不需要账号、定位、通讯录权限。
- 首版仅成人普通票，默认 1 人，人数可调整。混合席别人数不相加，至少同一车次的一种已选席别满足全部人数。

## 已确认范围

| 条件 | 行为 |
| --- | --- |
| 出发城市 | 默认北京，同城车站合并，可选具体出发站 |
| 出发日期 | 单日或连续日期范围；按乘客上车日计算 |
| 出发时段 | 默认全天，可选时段；以北京时间为准 |
| 车程 | 默认不限，包含长途和过夜列车，可设置上限 |
| 席别 | 默认全部，包括坐席、卧铺及无座，可筛选 |
| 路线 | 只查去程、直达，不查返程或中转 |
| 结果 | 按目的地所属城市汇总，展示具体到达站 |

不包含自动下单、抢票、候补提交、定时监控、旅游攻略或酒店推荐。北京本市目的地默认排除，因为本次目标是出城旅行。

## 三个页面

1. 条件筛选：出发城市/车站、日期范围、时段、席别、人数、可选车程上限。
2. 有票城市：城市名、符合条件的去重车次数、最短车程、最近查询时间；默认按最短车程排序，可按车次数排序。
3. 城市详情：日期、车次、出发站/到达站、出发/到达时间、跨日信息、历时、各席别的原始余票状态。可复制行程信息、打开 12306 官方查询页；只有验证过的跳转方式才能声称已预填条件。

本次验证阶段无需页面视觉稿。视觉样式在进入界面实现时单独完成，并遵守全局视觉规范。

## 查询与状态规则

- 唯一行程键：乘客上车日期 + 内部列车编号 + 上车站 + 下车站。同一城市重复查询产生的相同行程只计一次；同车次不同下车站是不同乘车选项，城市“车次数”按日期 + 内部列车编号去重。
- 城市归并使用数据源显式提供的城市标识和名称，不根据车站名称前缀猜测。字典里的行政归属不代表当日仍有客运班次。
- 先建立直达候选范围，再按日期/城市查询余票；不能用只查热门城市代替全国目的地覆盖。候选全集及查询覆盖不明确时，界面必须标明“覆盖范围尚未验证”。
- 完整结果需要覆盖所有候选查询单元。部分成功显示“部分结果”和已查/待查/失败数量，不能显示“已查完全国”。
- 只有可售车次且所选席别为正整数余票、人数不超过该值，才是数量已确认的匹配。
- 返回“有”但无数量时：1 人可视为有票；多人显示“有票，数量待核验”，不算人数已满足的确定结果。不得把“有”编造成精确张数。
- 无、0、候补、--/未提供席别、尚未开售、停售、查询失败、取消和缓存过期分别保留，不能都映射为“无票”。
- “预订”按钮/可售标记本身不证明任一席别有票。
- 查询时间使用本次实际收到响应的时间；读取缓存保留原时间。点开购买入口前重新核验选中车次，刷新失败必须明确提示。
- 日期区间两端均包含；时段按每日出发当地时间筛选，开始包含、结束不包含，全天覆盖 00:00–24:00，跨午夜窗口表示开始时刻以后或结束时刻以前。
- 跨日到达依据来源数据或经过验证的历时计算，保留 +1/+2 天，不把到达时刻更早当作负车程。
- 可售日期和起售时间根据来源当期规则判断。尚未开售不归为无票，不能仅硬编码固定预售天数。

## 架构边界

| 模块 | 输入与输出 | 责任 |
| --- | --- | --- |
| StationCatalog | 车站原始记录 → Station(code, name, cityId, cityName) | 字典解析、版本和更新日期 |
| CandidatePlanner | 出发站、日期 → QueryUnit 列表和覆盖说明 | 找出真实直达候选，禁止静默遗漏 |
| TicketSource | QueryUnit → QueryOutcome | 获取票源、记录来源时间；保留不可用/超时/协议变化 |
| SearchCoordinator | 筛选条件 → 查询进度和原始结果 | 前台执行、取消、去重、缓存和限制并发 |
| CityAggregator | 已验证车次 + 条件 → 城市与行程列表 | 席别/人数/时段筛选及城市汇总 |
| Compose UI | 查询状态 → 三个页面 | 不把失败或部分覆盖伪装成完整无票结果 |

数据入口独立封装，未验证票源前不把网页私有协议写进 UI。使用 HTTPS 和正常证书校验，保留平台访问限制。

## 首个交付阶段：票源和设备可行性

1. 正常读取官方查询页及其公开车站字典，核实城市字段、车站样例、当前查询路由和参数。
2. 选一个已开售日期进行少量只读查询。先验证北京至天津；正常会话可用后才能增加其他城市样本。
3. 用官方网页同条件查询核对结果。没有拿到真实余票时停止扩展，不启动全国扫描。
4. 检查真实直达候选全集及同城查询语义；缺少这一项即使单路线可用，也不能宣称“北京出发全部有票城市”可用。
5. 检查 JDK、SDK、adb、已连接真机；本次不修改用户已有模拟器、不安装手机软件。
6. 输出证据记录和判定：可用/部分可用/不可用。验证失败也是本阶段结论，但不是 App 已完成。

## 验收与失败处理

票源正式接入需要同时验证真实余票、席别含义、上车日期、同城站覆盖、全国直达候选覆盖、查询耗时和限制。一次成功不能证明长期稳定或获得正式开发者接口授权。

纯解析单元测试重点：候补不算有票、多人数不跨席别相加、“有”不编造数量、跨午夜、跨日到达、城市归并、重复车次和部分失败。不要依赖实时余票固定不变来写测试。

真机验收重点：APK 安装与启动、系统返回手势/刘海与状态栏、字体放大、联网、取消查询、前后台切换、打开 12306。模拟器通过不能替代 Mate 60 Pro + HarmonyOS 4.2.0 的实测。

若票源访问失败：保留 HTTP 状态、响应类型、时间和错误页面地址；不得归类为没有车票。完成可独立推进的设计与环境检查，明确列出剩余依赖，不交付假余票功能。
