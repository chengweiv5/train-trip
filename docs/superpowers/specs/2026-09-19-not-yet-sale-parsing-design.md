# 尚未起售车次的星号占位解析

## 需求与证据

用户要求继续修复此前已定位的尚未起售解析错误。2026-09-19 09:38:25 抓取的 2026-10-03 北京—天津响应共 310 条行程，其中 291 条明确标注起售时间、席别为 `*`。原解析器已识别车次 NOT_YET，却把席别星号判为 UNKNOWN，导致同一查询内全部行程失败。

## 方案

只在车次 SaleState.NOT_YET 时将原始席别 `*` 映射为新的 AvailabilityKind.NOT_YET，标签为“尚未起售”。保留 raw=`*`、原 saleText 和其他行程。该状态既不能确认有票，也不能进入数量待核验结果。

不把 `*` 全局解释为无票或本车次不提供；不跳过所有未起售记录，因为这样会丢失时刻和起售说明。availability(raw) 的无上下文调用继续把 `*` 作为 UNKNOWN。OPEN、SUSPENDED、CLOSED 车次的星号和所有其他未知值仍按现有协议错误处理。

## 集成边界

- 成功解析含未起售及已开售车次的混合响应，完整保留 trips，返回 QueryResult.Success。QueryResult.NotOnSale 继续只表示超出当前预售日期的整个查询项。
- Trip.isSaleable、confirmed、uncertain 的现有车次发售过滤仍生效；未起售记录不进入有票城市或待核验列表。
- 保留上一轮单项失败继续查询、错误查看、取消与仅重试失败项的行为。其未知协议测试改用真正未知值，避免把已支持的 `*` 继续当错误。
- 不增加起售提醒、未起售列表或查询次数；用户可在起售后刷新获得新状态。

先添加失败回归：一条真实 C2551 未起售记录、原始 310 条响应、已售/未售混合响应。覆盖星号在不适用发售状态下仍失败、未知值仍失败、非空票数在未售车次上也不能误报有票。

运行核心测试、APK 和 Android 测试 APK 构建及 lint。模拟器通过真实 TicketParser 接入离线混合响应，验证查询成功、只展示已开售有票车次；同跑上一轮失败隔离交互测试。版本升至 0.2.2 / code 6，按此前真机交付要求同签名覆盖安装并回读版本、包哈希、启动和偏好。
