# v2.0 自动排除受限需求并继续候补 · 当前设计

**2026-09-30 执行更新：** 用户已确认四主题配色，并明确要求“设计完成后直接进入代码开发”，锁屏未保存也不阻塞。原 17 屏颜色已应用并保存，core 状态机与持久化协调器已开始实现；Android 页面和真实平台适配仍未接入，未发真实订单。下文“先做设计”保留为原阶段背景，当前进展以[代码第一阶段记录](../../verification/2026-09-30-v2.0-core-foundation.md)为准。

用户已明确本版功能为：按条件筛选车次，选择车次和乘车人，提交真实候补订单。本稿取代“候补探测”和此前仍待确认提交语义的提案。不再要求确认是否接受订单创建；用户已经确定产品行为。当前任务仍是先做设计，不执行用户账号的真实下单。

**核心行为**：12306 明确拒绝某项候补需求时，自动从本次候选中排除该项，再提交剩余需求。用户一次发起，系统处理多轮“拒绝 → 排除 → 继续”，直到创建候补订单或全部候选均被明确排除。用户已授权这种产品行为，不能再将其降级为每次失败都让用户手动修改和重新确认。订单创建成功即停止，支付仍在 12306 完成。

## 主要流程

候补查询 → 筛选结果 → 选择车次与席别 → 登录（未登录时）→ 勾选乘车人 → 确认全部需求及截止兑现时间 → 一次提交全部所选需求 → 明确拒绝时排除对应项，再一次提交全部剩余需求 → 订单创建成功 / 所有需求均被排除。订单创建后，在 12306 支付。

候补页与原查票页采用相同的浅色主题、表单卡片、日期和时段控件、站点选择器及车次时间排版。底部导航为“查票 / 候补 / 想去”。候补条件独立保存，切换模式保留各自输入及列表位置。查票继续展示现票，候补页展示可以选择的候补需求及明确受限的席别。

## 查询和筛选

查询不要求先登录。所有查询和筛选集中在第 1 页，包括出发城市、目的地城市、出发日期、出发时段、席别、车种、最长车程、具体出发站、到达站及“只看可加入候补”；结果排序也在本页设置。城市可覆盖同城多个站，结果必须标明实际起终站。当前首页围绕一组出发/目的地城市展示；“想去”中的城市可携目的地进入候补页。跨城市探索暂沿用查票能力，不在本轮额外引入候补城市聚合页面。

日期复用现有选择器，候选查询范围受官方当前起售范围约束。原型以单日 10 月 7 日为例；日期范围查询可以拆成多个单日读请求，但可合入同一订单的日期和车次组合上限，必须按当前接口能力限制，不能把查询范围等同订单范围。查询结果可以包含 20 趟车，是否可将 20 趟全部选入同次候补订单需遵循当前官方限制；超限在选择或确认时说明并要求调整，不自动拆单、不暗中分组提交。

第 1 页参考实际查票页的 `FiltersScreen`：出发地采用整行入口，左侧显示标签和城市，右侧显示“同城各站”或已选具体站名，并有进入箭头。点击整行，在同一面板选择城市和该城市的车站。目的地使用同样的一体化行式入口；这是对查票页出发地交互的复用，不代表现有多城市目的地选择器已经支持到达站筛选。删除下方重复的“出发站 / 到达站”和仅为这些字段存在的“更多条件”容器。

两个位置入口各自管理城市及车站集合，同一份值同时用于显示和查询。“同城各站”表示当前所选城市内的所有可查询站，不是全国车站；选定单站后直接显示该站名，选多个站时按空间换行并提供可查看的完整列表。打开选择器回填当前城市和站点，搜索或更换城市后清空旧城市的站点选择；在当前城市可选“全部同城车站”或具体车站，点击“完成”一次应用，取消不修改原选择。站点均须属于当前城市，不能保留过期或异城站点。

日期、时段、席别、车种、最长车程、排序及“只看可加入候补”继续在第 1 页设置。默认过滤开关直接放在其他查询条件卡片中。选项选择器属于本页的字段控件，不再有另一套完整筛选页面。车种提供不限、高铁/动车、普通列车；出发时段可多选或自定义，逻辑沿用查票；席别可多选；排序提供出发最早、车程最短。筛选不能跨席别合计人数，也不按预估成功率宣称保证提交。

第 2 页仅展示已应用的条件摘要、车次和“修改条件”入口。点击后返回第 1 页并回填全部原输入，包括城市及站点集合；结果页不再提供独立筛选入口或日期快捷筛选。第 1 页保留编辑草稿，点击“查询候补车次”后统一应用并返回结果；未重新查询就返回时，继续显示旧结果及旧条件摘要，不能让新草稿与旧结果混用。查询失败保留本次输入以便重试。修改输入本身不会发起订单操作。

筛选只影响可见列表，已选候补需求保留在底部摘要和确认清单中；若有已选项被隐藏，明确显示数量并提供“查看已选”，不得静默提交用户已看不见的内容。更改出发/目的地或日期使已选需求不兼容时，在重新查询应用条件时提示并清除受影响项；乘车人名单保留。空结果中的“调整查询条件”和“查看受限车次”也返回第 1 页，后者定位“只看可加入候补”选项，保持用户显式修改后再查询，不在结果页维护第二份筛选状态。

## 选择车次与席别

一次选择单位是“乘车日期 + 列车标识 + 实际出发站 + 实际到达站 + 席别”。卡片中每种席别独立可选，多选采用方形勾选标记，并以边框和文字“已选”辅助。底部固定“已选 N 组候补需求 / 下一步·选乘车人”。相同车次的多个席别算不同需求，去重后计数，不把 N 组当作 N 位乘客。

状态文案：

| 来源状态 | 展示 | 交互 |
| --- | --- | --- |
| 支持候补、席别未受限 | 可加入候补 | 可勾选，仍可能在提交时被拒绝 |
| 席别限制标记命中 | 候补订单较多 | 默认隐藏；关闭过滤后可查看，但不可勾选 |
| 不支持 / 不提供候补 | 暂不支持候补 | 不可选 |
| 该席别有现票 | 有票，可直接购票 | 跳转查票并带入条件，不自动转成候补 |
| 未起售、数据异常 | 保留对应事实 | 不推断为可候补 |

“只看可加入候补”默认开启，重置筛选后也保持开启。按当前日期、准确区间及用户所选席别过滤灰色受限需求；车次在所选席别中仍有可候补项时保留，否则隐藏整趟车。例：仅选择二等座时，二等座为灰色的车次隐藏；同时选择一等座且一等座仍可候补时，保留该车次的一等座选项。不能因为一个席别受限就删除整趟车的其他可用席别。

默认列表不将受限项纳入可选候选数或自动提交集合。用户可关闭过滤查看受限席别及原因，仍不能勾选；未知、未起售或不支持状态也不能视为可候补。支持候补的入口状态不是指定乘客提交资格保证：蓝色候选在提交时被明确拒绝，才进入自动排除并续提流程。提交拒绝只属于该次请求，不能直接永久改写匿名候补状态。

前置检查可在进入订单确认前刷新车次及验证条件。需要登录或身份验证时在对应步骤提示；不能把 `checkTrain`、`checkOrder` 或概率预测包装为“5 人已通过”。车次组合、乘车日期数量、相邻日期要求、人数上限和重复订单限制从已验证的官方规则获得，原型不写死未确定限制。

## 登录与乘车人

在点击“下一步·选乘车人”后，未登录者进入登录入口，保留已选需求。已登录者直接读取乘车人。具体登录方式及会话接续需接入验证后确定；原型不承诺登录其他 App 或系统浏览器即可自动获取会话。

乘车人页显示当前账号、刷新入口、姓名、证件类型及尾号、票种、可用或待核验状态。用户多选实际乘车人，人数由名单计算；0 人不可继续。人数上限按官方规则处理。待核验或不符合资格者不可选并给出原因；空名单提供去 12306 管理乘车人的入口。姓名不因隐私遮盖到无法区分同姓旅客，证件尾号辅助辨认；图中为明确标记的虚构示例。

票种、儿童年龄、学生资格、联系方式等按对应官方流程核对。用户无需输入加密标识，程序使用当前账号与当前协议返回的乘客记录。`enc_no` 与网页 `allEncStr` 不混用。更换账号或登录过期后重新加载名单，旧乘客标识和判断失效；不能只按人数认定两个名单相同。

## 确认和提交

确认页一次展示所有已选需求，逐项列明日期、车次、实际区间、时刻和席别；下方显示全部已选乘客和票种，并提供编辑入口。截止兑现时间以服务允许的选项选择，最终显示明确日期与时刻；不同车次组合统一规则需按服务协议验证。原型的 06:20 为 10 月 7 日最早 08:20 车次前 2 小时的示例。

主按钮使用“开始自动提交”。紧邻操作明确“遇到候补过多时自动排除并继续，订单创建后立即停止”，同时显示“提交成功后需在 12306 支付”。完整摘要、自动处理说明和主按钮即为产品中的最终确认，不再为每轮排除和重提弹窗；官方必要验证仍由用户完成。自动付款、自动取消、添加用户未选择的车次均不在本版范围。

一次开始授权处理本次选定的全部需求，首轮全部一起提交；对已验证为明确未创建订单且能归因到某项需求的拒绝，自动删除该项，再将全部剩余需求一起提交。例：第 1 轮 A+B+C，A 被拒绝后第 2 轮 B+C，B 被拒绝后第 3 轮 C。这不是逐车次提交，也没有“后续候选组”。请求串行，任意时刻最多一个提交在途。服务异步处理时先等待确定结果，不显示虚构百分比。离开页面不会被描述为取消订单。查询订单以当前账号和已发请求上下文对应，不能误认其他历史订单为本次结果。

## 自动排除与续提规则

1. 开始时固定账号、真实乘客及票种、所选需求集合和绝对截止兑现时间。所有剩余需求同轮提交，不设置分组优先顺序。每次仅减少被拒绝的需求，不改人数、不换乘客、不切日期或席别来绕过拒绝。
2. 记录当前提交轮次和实际发送的需求集合。只有明确业务拒绝且本轮未产生订单时，才进入排除判断；“请求失败”不能统一当作“某车次不可候补”。
3. 优先用结构化错误中的日期、列车标识、区间和席别精确对应本轮项。若服务只给错误文案，必须先以真实脱敏响应样例验证提取规则，并确保在本轮集合中唯一匹配。仅含“某车次”但同名跨日或多席别时，除非协议明确拒绝整个车次范围，否则不能扩大删除。无法唯一识别时暂停，保留全部未确定项。
4. 仅从本次运行的剩余候选中排除；保留最初选择的快照和排除记录，包括原文、需求、时间、来源轮次。不会删除收藏、历史行程或用户保存的查询条件。下一次用户重新发起可重新选择，不能永久判定不可候补。
5. 自动继续之前，重建剩余需求对应的候补请求上下文，不能直接复用包含已删车次的 `enc_data` / `secretList`。保留原乘客、票种和绝对截止时间，按官方返回的合法规则复核；必须重新取值或验证时不伪造验证参数。
6. 本轮至少排除一项才允许自动发下一次提交；重复拒绝已移除项、错误匹配不在本轮、集合未缩小等情况暂停，避免空转。遵循服务返回的等待间隔与限制，限流/验证码/风控时暂停，不并行提交或高频重试。
7. 剩余集合非空则将全部剩余项一起提交，集合空则结束。订单创建成功就停止，展示订单实际包含的需求和已排除项。若订单返回的需求集合与本轮发送集合不一致，核对差异，不把未确认入单的部分自行重新提交。
8. 只有全部原候选都得到明确拒绝或不兼容的可证实排除、且没有在途/未知请求或已创建订单时，才展示“全部候选未能提交”。20 趟车只失败 19 趟、另一趟超时，结果必须是“19 项已排除 / 1 项待确认”。
9. 停止按钮阻止下一轮请求；当前请求已发出时继续核对其最终结果，显示“已停止继续提交，正在核对本轮”，不能宣称撤销订单。进程重启或回到页面先查未决请求；没有确定结果前不自动重发。

在全部被拒绝且每轮至少移除一项的正常链路中，逻辑提交轮次不会超过原始候选需求数。资格错误、网络失败、账号限制等不消耗某个车次的“失败资格”，而是暂停原因，不作为排除依据。实现必须验证原子拒绝语义；若接口可能部分成功，先处理已创建订单和未决部分，不能盲目对原集合续提。

### 所有剩余需求一起提交与组合限制

“一次全部提交”指同一请求包含全部所选且符合官方组合限制的候补需求。排除拒绝项后下一轮仍提交全部剩余项。列表排序只影响浏览，不产生先后尝试的车次队列。

若实际规则不能将 20 趟一起提交，选择/确认页说明具体超限原因，由用户调整为合法集合。不能自动拆成每组 5 项或多张订单，也不能承诺突破平台限制。此前设计中的自动分组与“后续候选”统计已撤除。

### 进度与明细

运行页展示“最初选择 N 项 / 已排除 X 项 / 剩余需求 N-X 项”。操作卡明确“第 K 次提交 · 全部剩余需求”，列出本轮所有需求；同步显示 5 位乘车人。剩余数量不代表成功数量；订单是否创建由本轮返回决定。没有“后续候选”指标。

最近动作示例：收到“G374 二等座候补人数过多” → 已排除该需求 → 第 2 次提交 G652、G654。排除记录可展开查看原文和准确日期区间。日常可归因拒绝自动处理，不打断用户。用户可以停止，完成页可查看全过程。

**尚待接口样例验证**：已有官方客户端代码只证明会显示 `error_msg`，尚未拿到用户这类拒绝的实际返回结构，也没验证其中是否总能定位准确车次/席别。设计可以明确自动流程，但不能声称精确归因和续提已运行验证；该证据是开发实现的必要条件。

## 结果与恢复

- **已创建待支付**：立即停止自动续提，展示服务返回的订单号、预付款、支付期限、乘客和实际入单需求，另列自动排除记录。主按钮“打开 12306 支付”；不假定外部 App 可以直达指定订单。返回应用时刷新状态，不以“已打开 App”推断已支付。若服务异常返回多个订单，逐一核对展示，不能只取首条而隐藏其余订单。“成功”指订单已创建，不等同支付成功或候补兑现。
- **可归因的候补过多拒绝**：自动排除该项并继续剩余项；全部候选耗尽后才展示结束页面，保留逐项原因和原名单。
- **其他拒绝或无法定位的错误**：暂停自动提交，展示原因和保留的需求。用户处理必要条件后继续；绝不随机删一趟车来试。
- **提交超时 / 结果未知**：展示“正在核对订单”，先检查服务端订单状态，不把网络失败等同没有创建。未确定之前不提供再次提交。查询暂未发现订单也需考虑处理延迟；恢复后展示确定结果。
- **登录失效 / 需验证**：保存已排除记录与剩余候选并暂停，提示重新登录或完成验证。恢复后核对当前账号、乘客和未决订单；相同条件下提供“继续剩余需求”，不要求用户重新添加车次。恢复前若本轮可能已被受理，先核对订单。
- **无符合条件的车次**：提示调整日期、席别或时段；有受限项目被筛选时说明可以展开查看。查询失败单独展示并可重试，不能显示“没有候补车次”。
- **停止或退出**：保留本轮状态并停止后续提交，不会取消已创建订单；未确认结果在回到候补页时继续核对。若只是界面退后台，设计默认暂停下一轮并提示保留进度；后台持续执行需单独实现 Android 生命周期和运行提示，不宣称静态原型已支持。
